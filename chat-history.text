Observed errors (what happened when I tried to build)
- "no matching function for call to ‘gem5::DmaDevice::DmaDevice(const gem5::SimdAccelParams&)’"
  - This indicates the generated `SimdAccelParams` did not include the DmaDevice fields (so DmaDevice(p) signature didn't match).
  - Suspected cause: Python SimObject params did not cause the generated `SimdAccelParams` to inherit `DmaDevice::Params` (often because Python SimObject used multiple SimObject bases or SCons wrapper issues).
- "invalid new-expression of abstract class type ‘gem5::SimdAccel’" with note that pure virtual `getAddrRanges()` is missing.
  - Fix applied locally: added `AddrRangeList getAddrRanges() const override;` in simd_accel.hh and implemented it in simd_accel.cc to return `BasicPioDevice::getAddrRanges()`. (Make sure you still verify this after params regenerate.)
- Python wrapper & SCons issues:
  - SCons expects a SimdAccel.py wrapper in some cases. Creating that wrapper caused circular import / _params not present errors when implemented naively. The wrapper must not trigger an import cycle or expect generated params too early.
  - Solution approach: keep SimdAccel.py as canonical SimObject. Make SimdAccel.py a minimal shim that does a lazy import of `m5.objects.SimdAccel` or safely loads the python object file via file path so SCons can find it without causing circular import.
